# A4 思考过程展示行为清单（供真机逐项对照）

> 目的：handoff A4 中用户表示"思考过程……做的还是不好"但未说明具体缺陷。
> 本清单按当前实现的**真实行为**逐项列出可观察表现，供用户在真机上逐项
> 对照勾选（正常 / 异常+描述），拿到具体缺陷后再另开轮次修复；
> 本轮不改任何 UI 代码。核对依据：`src/trivae/interfaces/tui/models.py`
> `_apply_thinking_*`、`src/trivae/interfaces/tui/widgets.py::ProcessRow/render_thinking_detail`、
> `src/trivae/query/streaming.py` thinking lifecycle。

## 使用方法

对每一项先问自己「是否与该行描述一致」：
- 一致 → 打 ✅
- 不一致 → 打 ❌ 并附一句现象描述（最好截屏）
- 无法观察 → 标 N/A

## 清单

### A. 分段与顺序

- [ ] **A1 每个模型回合独立分段**：一次提问涉及多个工具调用时，
      工具前后的思考各是独立的条目（"正在思考"/"已思考 · n s"多行出现），
      而不是合并成一行连续文本。
- [ ] **A2 顺序与执行顺序一致**：思考段落出现的先后与实际执行顺序相同
      （thinking:1 → 工具行 → thinking:2 → 工具行 → thinking:3 → 回答）。
- [ ] **A3 第一段之后的思考不再回写第一段**：后续段落的内容绝不会
      出现在第一段的展开正文里。

### B. 隐私边界（正文来源）

- [ ] **B1 只展示 provider 公开摘要**：能看到的思考正文只在 DeepSeek 明确
      提供 public summary 时出现；看不到 provider 私密 CoT 或 SDK 内部字段文本。
- [ ] **B2 无公开摘要时只有活动行**：若该回合没有公开摘要，只显示一个
      "正在思考"行（带 spinner），随后变为"已思考 · n s"或关闭；
      **不会**凭空制造思考文字。
- [ ] **B3 无正文的思考行不可展开**：纯生命周期思考行没有 ▸/▾ 展开符号，
      点击/键盘都不会假装展开出空内容。

### C. 展开与折叠状态

- [ ] **C1 运行中默认展开**：有公开摘要时，思考正文随流式增量实时增长可见
      （spinner 状态下直接能看到文字滚动）。
- [ ] **C2 完成后自动折叠**：该段结束时标题变为"✓ 已思考 · <时长>"并自动收起。
- [ ] **C3 完成的时长合理**："· n s" 与实际该段耗时同量级（不是 0s 或明显异常值）。
- [ ] **C4 手动展开保持**：完成后手动展开一段思考，其后的自动行为不会再把它收起。
- [ ] **C5 手动收起保持**：运行中手动收起一段思考，它不会立刻被强制弹开。

### D. 正文质量与边界

- [ ] **D1 正文完整且有序**：展开后可见该段全部公开摘要文本，
      中文显示正常（无双宽字符错位导致的乱序感）。
- [ ] **D2 超长有省略标注**：正文极长时保留尾部约 1800 字符并明确显示
      "…（前面部分已省略）"，不会无声丢弃。
- [ ] **D3 折叠组内的思考同样可展开**：本轮结束后过程折叠为"执行过程 · N 步"，
      展开 group 后思考行仍可继续展开查看正文。

### E. 异常路径

- [ ] **E1 中断不留 spinner**：Ctrl+C 中断时正在进行的思考行立即结束
      （不保留转圈动画），本轮以错误行收尾。
- [ ] **E2 失败不留 spinner**：provider/查询失败时思考行同样收敛为已结束状态。
- [ ] **E3 中断轮的思考仍可检查**：失败/中断轮的过程组默认展开，
      思考正文仍可展开复查。
- [ ] **E4 思考正文可复制**：拖选思考正文可产生原生选择，Ctrl+C 复制的是所选文本
      而不是触发中断。

## 已知设计取舍（非缺陷）

- 思考行视觉上刻意低调（muted/dim），与回答形成对比 —— 这是 R5 明确要求的层级策略。
- 思考正文有界展示（≤1800 字符尾部），设计目标是不把超长推理淹没视口。
- 过程折叠组默认收起（成功轮），需要手动展开才能看到全部步骤。

## Provider 事实登记（handoff A5，2026-08-27）

> 用户反馈：思考正文「量偏少且是英文」。按 R1 契约，TUI 只能如实显示
> `thinking_visibility="public_summary"` gate 后的正文——正文的有无、长短、语言
> 全部由 provider 决定；TUI 不做翻译、不补写、不改 prompt（out of scope）。
> 本节只登记现象与待验证假设，供后续轮次决策。

**已确认事实**：

- F1 用户真机观察到 public summary 正文偏短，且内容为英文；
  TUI 端无任何截断告警时的长度上限为 `_MAX_THINKING_CHARS=1800`
  （超长会显式标注省略），因此「偏少」不可能是 TUI 裁剪造成，
  只能是 provider 发来的公开摘要本身就这么长。
- F2 语言为英文同理：`streaming_text` 内容 = DeepSeek reasoning summary 原文，
  TUI 链路（streaming → models → widgets）不存在翻译或改写环节
  （可对照 `query/openai_adapter.py` 中 public_summary 标记逻辑确认）。

**待真机/官方文档确认的假设**：

- H1 DeepSeek API 是否提供控制 reasoning summary 输出长度或语言的请求参数？
  （若存在且适配成本可控 → 另开配置类任务，不在本任务范围。）
- H2 英文摘要是否随 `model` 版本 / `reasoning_effort` 类参数变化？

*若后续确认 provider 输出策略可配，将「thinking 展示优化」另开任务处理；
在此之前保持 R1 的原状显示语义不变。*
