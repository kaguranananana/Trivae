# 讨论检索质量优化：证据与待评审方案

状态：已完成只读诊断与生产工具重放；产品代码尚未修改，待用户评审后建立任务实施。

## 目标与已确认需求

用户希望借鉴本次人工核对的检索方式，改善 Agent 学习讨论回答的完整性、准确性和有效信息密度。
首先解决真实 Trace 中的关键回复漏检、发言者误归属和日期误写；策略适用于需要提问、回复、建议和材料的讨论调查，不能为单条消息添加例外。

## 人工核对实际上做了什么

1. 使用 `rg` 定位 Trace 的提问、实际工具参数、结果和最终状态。
2. 使用 Python 标准库 `json` 读取事件，读取 SQLite 中已保存的完整答案；Trace 是经过 capture 的投影，不用短文本片段代替完整答案。
3. 使用 Python `sqlite3` 的 `mode=ro` 查询原群消息；固定群、消息定位符和时间范围，不把其他群或范围外消息混入结论。
4. 围绕已命中的关键提问，读取前一分钟与后几分钟的聊天，核对相关回复、发言者和时间；相邻消息只能提供上下文，不能自动认定直接回复关系。
5. 比较回答声称的内容与原始消息，然后沿发现的材料名或主题补查缺口。

这是带有已知线索的人工审计，有更多检查时间，也没有产品每次三轮工具的限制；它不证明人工核对已穷尽全部相关讨论，更不证明存在更强的新向量检索算法。

## 真实问题与归因

来源：`trace-c61ed0f5f2c64fd88229d8c398be5947`，原范围为 `qq:1039179741`，工具实际绝对时间 `[1785542400000, 1786844190001)`。

- 7 次工具调用、3 轮：3 次 semantic_search、4 次 lexical_search，0 次 get_message_context。
- Semantic 首轮使用最近 30 天和未限定时间的两条查询；后续才添加原用户指定的起始日期。实际时间条件不一致。
- lexical 搜索教程已返回 Red Herring 的后训练提问，但没有沿提问进一步查看后续讨论。
- 提问后约两分钟，在串中说“我觉得直接去看build a llm from scratch就行了”，随后说“这本书很详细”；正文却称“明显未被回答”。这是已证实的回复漏检和错误否定结论。
- “调用个api谁都会”和“这也能叫agent吗”来自提问者朗易思听，被正文归到 joye。工具已有 author，属于生成阶段事实归属错误。
- HuggingFace Agent 课程相关记录实际为 2026-05-21，岗位能力记录实际为 2026-05-31；正文写“4 月前后”。当前模型消息投影只给毫秒 timestamp，缺少可直接抄用的 UTC 日期。
- 8 月 14 日的《深入理解ai agent》询问没有进入回答；正文列出多个未证实与学习有关的 GitHub 项目。
- 当前 Prompt 的资源清单规则多次要求先搜 github.com，而本题主要需要讨论中的提问、对应回复和材料。这些指导存在误分流风险；它是待验证的生成行为归因，不是已经证明的唯一原因。
- 工具预算耗尽是执行终止事实；本例不证明需要增大预算。已有轮次先花在若干搜索上而没有关键回复深挖。

## 只读实测

重放命令：

```sh
.venv/bin/python .trellis/workspace/anontokyo/retrieval_quality_probe.py
```

脚本走正式 Tool → Capability → Canonical Read → ToolResultRecord → Model Projection，不调用 Provider，不写入消息、会话、索引或 Trace。
结果保存于同目录 `retrieval-quality-results.json`。

| 参数 | 返回消息数 | 书籍推荐进入模型输入 | “这本书很详细”进入模型输入 |
| --- | ---: | --- | --- |
| 前 2 条，后 2 条 | 5 | 否 | 否 |
| 前 2 条，后 8 条 | 11 | 否 | 否 |
| 前 2 条，后 20 条 | 23 | 是 | 否 |
| 前 2 条，后 40 条 | 43 | 是 | 是 |

四组在现有 16k 单次模型投影预算内均未截断；后 40 条组估算为 4163 token，该 estimate 不是实际 Provider usage。
这证明现有工具能够获取并投影证据，不能证明模型会主动选择这些参数，或会正确理解材料的适用背景。

同范围内 `教程` 返回 4 条，`agent` 返回 65 条；后者包括后训练观点和 8 月 14 日书籍询问。
这是对应关键词集合的完整返回，不等于 Agent 学习主题召回完整，也不能用命中数证明整体答案质量。

## 建议的最小实现边界

在现有独立 lexical/semantic 路径、显式 context 工具、一次软规划和 SDK Loop 内优化指导与模型输入事实。
不增加工具、不自动执行 Plan、不增加关键词判断器、不替换检索算法、不扩大默认轮数、不设置专用案例分支。

## 预期执行方式

先按用户主题和时间定位讨论；如果已经找到重要提问但回复证据不充分，下一轮优先显式读取后续上下文。
多个相互独立且已知来源的关键提问可以放在同一工具轮读取。邻居只是上下文，需通过提及、回复定位或连续话题来判断关联。
随后只对未覆盖的具体需求补查材料名、相关主题或另一条检索路径；不因收到某种泛类别词就把讨论任务变成 GitHub URL 清单。
最终对“谁问、谁答、什么建议、什么材料、适用背景、还有什么未知”给出有证据的解释；群友没说过的背景判断须标为归纳。
搜索结果或局部窗口没有回复时写“已查看的范围内未确认”，不写“无人回答”或“唯一建议”。

这些都是 Agent guidance，不能声称机器已经保证每个问题都完整处理。

## 验收与实验设计

- 正式工具重放必须能把已知推荐和后续解释投影给模型，来源可引用，日期与 author 保留。
- 新 UTC 字段与 canonical timestamp 一致，模型投影容量和 trimming 测试保持通过；不声称增加日期字段能消除所有日期错误。
- 用 SDK 回归确认每轮预算提示与真实消费一致，达到三轮后仍进入原 final synthesis，不加隐藏额外轮次。
- 固定原问题、群和数据、Provider/model、工具预算及路由/Plan；保存当前版本与候选版本完整 Trace 和答案做配对检查，重复运行观察模型方差。
- 对本案例检查具体书籍推荐是否出现、提问者观点是否仍被误归属、5 月来源是否仍被写成 4 月、8 月书籍询问是否召回，以及无关项目是否仍占据主要篇幅。
- 再验证纯 GitHub 资源清单、简单事实查询、明确零结果和局部回复调查，确认讨论指导未破坏已有用法。
- Provider-free 测试只能验证 contract；ScriptedModel 不能作为自然语言遵从或答案质量改善证据。质量结论以真实运行及逐项消息核对为准，不使用字数、工具次数或 finalization=valid 当质量分。
- 若只读召回已正确、模型仍忽略证据，先记录 Answer Generation 反例；不能把问题掩盖成检索失败，也不能用固定关键词 Judge 或补丁改写答案。

## 关键取舍与责任

- Responsibility / Ownership：Retrieval 继续负责 canonical 召回和边界；工具描述解释参数；Runtime 编译预算提示；Evidence 只派生可信时间显示；模型负责话题关联和自然语言归纳。
- Why not：目前已有工具能送达丢失证据，引入 reranker、混合召回、全群扫描或新的证据状态机没有足够必要性证明。若受控实验发现相关提问在两路都稳定召回不到，再讨论检索层演进。
- Failure / Observability：真实反例是回复漏检、错误否定、作者与日期误写；将参数、context 消息、模型输入投影、预算和正式答案保存在现有 Trace 中，不新增第二套日志链路。
- Scale / Performance：显式深挖只围绕关键来源，预期减少无效宽搜，但延迟和 token 改善尚未实测；更大消息窗口可能混入更多闲聊，必须通过实际质量与成本观察判断。
- Boundary：不改变 canonical schema、索引、当前范围权限、Citation finalizer、Conversation transaction 或 Provider 配置；不假装主题全量召回已经实现。
- Evolution：若三轮下仍稳定存在必要未完成调查，再基于 Trace 讨论预算或停止策略；不是预先把预算调大。
- Interview Defense Notes：问题证据见原 Trace 与 canonical 消息；工具能力证据见 probe 输出；方案是已有能力的指导和事实展示优化；“模型整体质量提升”目前没有实测证据。
