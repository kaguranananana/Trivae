# Capability Suite：用户问题优先候选

> **历史候选记录（2026-10-28）**：该候选用于记录一次题集设计与证据审查，不是当前发布 Suite、待办或 Baseline。后续 Runner 和评测流程可能已变化；当前实现以源码及 [PROJECT_STATUS](PROJECT_STATUS.md) 为准。

本候选针对旧 `capability@v2` 的问题来源偏差：用户通常不知道群里已经讨论过什么。旧 Suite、Case 版本、运行、Review 和历史实验均保留；新身份是 `capability-user-first-candidate@v1`，仅供设计与人工审查，不是已发布的 v3、盲测集或新的 Baseline。

## 审查与冻结顺序

先仅根据旧 30 个题面判断是否预设讨论内容：27 题明显、2 题存疑、1 题较自然。该分类是题面诊断，不是对作者实际编题过程的证明；具名技术并不自动意味着题目不自然。旧问题和逐题理由在本机私人审阅稿中。

以本轮用户给出的真实问法示例及常见开发、求职需求起草 30 题，2026-10-28 11:32:35 +08:00 将问题、用户需求和自然性理由写入单独的只读候选文件。之后才对本轮候选逐题检索聊天消息。没有根据检索结果改题或要求候选一定可回答。题目以固定用户需求为中心，跨群、时间和多观点来自找到的材料，而不是提前写进题面。

此过程由同一个 AI 完成，冻结前已读过旧题题面、项目状态和旧评测说明，其中包含部分已有讨论线索和实验结论。虽然没有针对新题预先检索原始消息、也没有根据本轮检索结果改题，仍无法保证题目设计完全不受已有线索影响；这不是对旧题双盲，也不是独立的人类审核。文件只读和时间记录是过程记录，不是不可篡改的证明。表达风格依据用户本轮示例，不声称分析过用户全部历史提问，也不把 30 题当成随机抽样后的真实查询分布。

## 数据与证据边界

复用冻结的 864,615 条 canonical 消息、词法索引和转发投影，检索覆盖多组原词及同义词；每组取相关性前 18 条，近期问题另按时间取前 18 条，部分问题增加定向检索及相邻消息。参考覆盖 8 个会话、74 条 Case 内消息记录、66 条不同消息；搜索和人工助手筛选均非穷尽。未调用 Agent、模型评测或外部 Judge。

问题时点为 2026-10-28 11:32:35 +08:00；“最近”初审采用从 2026-09-28 00:00 开始的窗口。该冻结库最新消息为 2026-10-27 21:44:51 +08:00，不能假设各群均完整覆盖至同一时点。旧于窗口的参考只可作为明确标注日期的背景，不能冒充近期使用。

Case 中的 `time_context` 当前只是评测元数据：现有 `EvaluationRunner` 创建 `QueryRequest` 时没有传入该字段，也没有保证执行时的“今天”固定为上述时间。未来实际运行前，须通过评测环境明确固定或传递时间并验证其生效；不要把时间硬塞进用户的自然问题，也不能将之后按新时间解释的运行与本次候选直接比较。本轮没有修改 Runner 或产品链路，也没有验证未来时间注入。

助手初审认为 20 题暂时覆盖主要需求、10 题部分充分、0 题未检得相关证据；三个标签都只是本轮有限检索下的暂定判断，人工确认数为 0。这里允许出现“未检得相关证据”，不会为了得到负例或满足比例删除、改写问题；没找到不等于全库或现实中不存在。

每题包含原始自然问法、用户需求、自然性理由、必须完成的任务、带消息身份的候选事实、信息性质、局限和其他合理答案。原消息可核实的是谁在何时说了什么；群友体验、推测、转发和机器人建议均不自动成为外部事实。开放问题以完成用户需求和引用足以支持的事实为准，不要求复述所有参考锚点或命中固定消息 ID；证据只支持部分问题时，应保留可回答部分和缺口。未来若检索到新的有力证据，可以接受其他合理答案并另建新的经审核 Case 版本，不反向改动冻结问题。

## 文件和检查

仓库内只提交不含私人原文的 `evaluation/suites/capability-user-first-candidate-v1.json` 及设计说明。私人材料保留在 Git 忽略的 `data/evaluation/capability-user-first-20261028/`：

- `review.md`：旧 30 题题面审查、新 30 题及每题候选 Ground Truth，引用摘录可能截断。
- `candidate-pool-frozen.json`：检索前冻结的问题、用户需求和自然性理由；`old-question-audit.json` 保存逐题旧题审查。
- `cases/` 与 `suite.json`：兼容现有 Evaluation Case/Suite 契约的独立候选，所有引用和语义均未裁决；`candidate-ground-truth.json` 以更易阅读的结构保存每条事实、证据限制和可接受的其他答案。
- `evidence.json`：完整原始正文、消息 ID、会话、时间、作者身份；转发消息另记录 root、parent、path 和原始时间。`retrieval-candidates.json`、`deep-search-*.json` 保留本轮检索词、结果数量和候选；`supplementary-search-log.json` 补记近期排序和邻近读取的方法，具体执行秒数未单独保存。
- `design-verification.json`：题面未改变、身份、来源及原文的检查摘要。验证不证明语义蕴含、查询穷尽或自然度。

本轮 30 个 Case 均通过现有 Case 合同校验；引用消息经原始冻结库逐字段回读，结果与私人证据包一致。现有 `audit_capability.py verify` 可以核验当前每题均有参考消息的候选，但其实现要求至少一条引用，**不能**用来验证未来零证据题。私人 `verify_design.py` 允许“未检得相关证据”且不伪造来源；后续若正式采用此类题，须先选择支持空证据的审核和评分方式，不应将技术校验失败解释成无证据。设计稿的“充分/部分充分”也不能直接转换成对 Agent 的自动通过或失败。

后续应由人工逐题核对问题是否自然、来源是否支持结论、近期范围、关键要求与可接受替代；真实完成审核后另存 Case 版本，再决定是否开展小规模评测。不得把本候选的参考锚点视为穷尽，也不得把本轮结果与旧 Suite 的部分运行混算。
