## 1. 实验目标与口径

此前语义增量索引的真实模型验证停留在 `150 → 152` 条合成消息（`18` 个分块，`8.80s → 3.77s`）。本实验改用本机真实冻结主库，验证**千级真实群聊消息日常追增**下，局部时间连通段重切 + 精确输入向量复用在十万级分块规模下的实际复用率、耗时、数据一致性与全量重建对比。

### 关键实验约束

- **工作库隔离**：严格复用 `trivae.evaluation.workspace.EvaluationWorkspace` 与 `data/evaluation/frozen-20261028-validated/freeze.json`，通过 APFS `clonefile` 建立独立工作库，结果持久化后自动回收；未修改主冻结库、线上库或原始导出目录。
- **真实增量批次**：选取冻结快照之后按时间顺序紧邻的真实定时导出批次 `*_20261028_10*.json`（8 份群聊 JSON，未人工筛选或合成），共接收 `1,555` 条原始记录，幂等入库新增 `1,386` 条、去重 `169` 条、冲突留痕 `3` 条、错误 `0` 条。
- **零 Mock 推理**：全程使用正式 `SentenceTransformerEmbeddingProvider`（`Qwen/Qwen3-Embedding-0.6B`，1024 维，`last_token`，归一化，`batch_size=8`，长输入 `>2048` 字符隔离）与真实 `sqlite-vec 0.1.9`，离线缓存加载（`HF_HUB_OFFLINE=1`）。
- **全量重建基准口径**：单次全量重算 `104,935` 个分块在本机 MPS 上需数小时，因此采用**三层互证**：
  1. 全库真实流式扫描与分块（`882,729` 条消息完整跑完 `SemanticChunker`）；
  2. 在完整流式分块上做 `16 × 64 = 1,024` 块系统分层连续窗口采样（保持真实相邻分块 batch padding、长输入隔离与真实 `sqlite-vec` 写入），计算均值与 95% t 置信区间外推全库耗时；
  3. 只读核对本机 `data/trivae.sqlite3` 中 `auto_import_runs` 的 2 次历史真实全量重建墙钟记录作为独立旁证。

### 样本代表性与分段吞吐

- **长度分布匹配**：全库 `104,935` 个分块的 `embedding_input` 字符均值 `327.67`、中位数 `285`、P90 `464`；分层采样的 `1,024` 个分块（16 个等距连续窗口 × 64 块）均值 `333.94`、中位数 `275`、P90 `498.2`。样本中 `>2048` 字符长输入隔离比例为 `0.78%`（8/1,024，全库为 `0.11%` = 115/104,935），略高于全库，但 16 窗口吞吐区间（`1.63–5.05 chunks/s`，整体 `3.29 chunks/s`，均值 `303.85 ± 110.51 ms/chunk`）的外推结果 `8.89 h`（95% CI `7.18–10.61 h`）与历史 78.9 万–79.7 万规范消息两次真实全量重建（`7.94 h`、`7.43 h`）量级高度一致。
- **并发与热态波动说明**：本轮正式运行期间本机同时存在另一个独立评测进程占用系统资源，因此在同机空闲状态下的两次前置试跑中，同批次冷启动增量耗时曾分别测得 `109.87 s`（embed `68.44 s`）和 `121.94 s`（embed `84.60 s`），低于本轮正式配对的 `223.56 s–231.30 s`。本报告以同会话配对的 `223.56 s / 8.89 h` 作为主口径，不跨负载拼接最快增量与最慢全量。

## 4. 正确性与一致性验证

1. **全库 104,935 分块 100% 逐行等价**：在增量更新后的工作库上完整执行一次全量流式分块（`132.69 s`），逐字段比对全部 `104,935` 个分块的 `chunk_id`、`parent_id`、`session_id`、起止消息 ID、起止时间戳、`message_count`、`effective_chars` 与 `embedding_input`，结果 `missing_in_expected = 0`、`missing_in_actual = 0`、`field_mismatches = 0`（`104,935 / 104,935` 完全一致）。
2. **新增向量数值一致性**：对增量新算的 `197` 个向量独立重算并比对 `semantic_vectors_1024` 存储的 `float32` 向量，最大绝对误差 `7.42e-09`（远低于 `1e-4` 容差）。
3. **索引完整性与检索烟雾**：`integrity_report.status == "valid"`（`metadata_chunk_count = vector_count = 104,935`，`missing = 0`，`orphan = 0`，采样范数最大偏差 `5.08e-09`）；真实语义检索烟雾返回 `5` 条命中（`top_score = 0.888338`）并恢复 `72` 条原始规范消息。
4. **幂等空更新**：紧接二次调用 `builder.update()` 进入 `build_mode = "unchanged"`，耗时 `2.04 s`、`embedding_count = 0`、模型调用与 `preload` 增量均为 `0`。

## 5. 局限与已知瓶颈

- **全量耗时为外推 + 历史旁证，非同会话 9 小时完整重跑**：严禁写成“同次实验实跑 8.9 小时全量重建”；必须说明 `8.89 h` 来自 `1,024` 块系统分层采样（95% CI `7.18–10.61 h`），并由本机历史 `auto_import_runs` 两次 `7.43–7.94 h` 全量运行交叉印证。
- **增量更新为分钟级，非秒级**：千级消息（`1,386` 条 / `197` 新块）下，单本地 M4 MPS 运行 `Qwen3-Embedding-0.6B` 的增量更新为 **~2–4 分钟（正式配对 3.7 分钟，轻负载 1.8 分钟）**；只有无变更空更新在秒级（`2.0 s`）。
- **已定位的非 Embedding 固定开销（~62–77 s）**：增量更新除 `142.6 s` 模型编码和 `3.8 s` 写入外，仍有约 `62–77 s` 消耗在转发消息全库清单同步与事务前完整性扫描（与既有限制“转发 inventory 在 revision 变化后仍扫描全库 root JSON”一致），是后续可继续优化的明确工程瓶颈。
