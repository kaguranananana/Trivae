# CJK 检索实验：简历证据与面试解释

实验日期：2026-10-20。完整数据与边界见 [实验报告](../evaluation/experiments/cjk-bigram-v1/report.md)。本材料不把字面覆盖率等同于 Agent 准确率，也不把 AI 审核称为人工审核。

## 可用简历 Bullet

围绕 SQLite FTS5 CJK bigram v2 搭建可复现检索 A/B 评测，在 82.38 万条普通/转发消息投影、64 条固定查询上复用生产 Scope、BM25 排序与 Evaluation 指标；44 条中文及混排查询的全深度字面覆盖率由 **3.19%（2,853/89,346）提升至99.99%（89,340/89,346）**，Recall@10 macro由 **10.17%提升至14.68%（+4.51个百分点）**，并识别混排误匹配、单字漏召回和索引空间 **+37.18%** 的代价。

口述时必须补充：89,346 是 query-message pairs；全深度覆盖不是前十覆盖；64 条是人工选择的诊断查询，既非随机线上流量，也非未见测试集。可说“完成8题有界真实Agent验证，保留失败与中断”，不可说“证明端到端准确率稳定提升”。具体个人职责须与本人实际承担的工作一致。

## 一分钟解释

原先 unicode61 会把连续中文，甚至相邻的中英混排，看成一个完整 token，所以消息中有“真心推荐”时，搜索“推荐”可能找不到。v2 把中文连续段转换成重叠双字词，并在中英交界加空格。查询也做相同转换，再用有序 phrase 匹配。这样能找回中文子串，但仍保留英文 token 的精确匹配语义。

我用同一个真实快照和64个冻结查询比较两种索引，复用生产投影、权限范围和排序，并逐题检查实验 Candidate 与生产结果一致。44条中文/混排查询的全深度字面覆盖从3.19%到99.99%，但前十Recall的提升只有4.51个百分点，因为常见词在旧索引里也已有10条命中。代价是索引文件增加37.18%，SQL查询也更慢；还有3条混排查询的前十结果退化。真实模型验证没有证明稳定端到端收益。

## 为什么原始 FTS5 会漏召回中文短词？

FTS5 unicode61 按 token 匹配，不会把连续 Han 字符自动分成中文词。文档 token“真心推荐”不同于查询 token“推荐”；`repo推荐这个`还可能成为一个混合 token。索引行存在、总数正确也不能证明分词后能命中。原始故障用 fts5vocab 观察 token，再用相同 Scope 的正文枚举确认漏召回，因此不是“没导入消息”或索引 stale。

## Bigram 原理与取舍是什么？

“真心推荐”转换为“真心 心推 推荐”；“推荐这个”转换为“推荐 荐这 这个”。查询归一化后整个 Han 段按有序 phrase 匹配，而非把多个 bigram 当作任意位置的 OR。v2 还将每个 Han 段两侧分隔，使“abc推荐”成为“abc 推荐”，修复 v1 的混排边界问题。

选择 bigram 是为覆盖常见的双字中文查询；历史 trigram 探针对双字“推荐”无法匹配。没有引入中文词典依赖，也没有给生产查询加 LIKE fallback。取舍是 token 数量与索引空间增加、单字不能命中多字段内部、混排分隔写法会产生字面额外命中。ASCII 仍按 token，不保证“hr”命中“hrbp”。

## Benchmark 怎样保证 A/B 公平？

先用 SQLite backup 取一致快照，普通与转发子消息使用同一生产投影；转发预览不纳入索引，内部重复转发保留独立 occurrence，Scope 按外层时间处理。只改变索引/查询两侧的 CJK 归一化，A 不写入伪造的 v2 metadata。

查询、全会话 Scope、limit=10、BM25 及时间/序号/ID平局顺序相同，B的64条 count/top10 全部与生产一致。正式执行前冻结 Reference 与配置。原始 LIKE Oracle 在 NUL 后漏读是测量缺陷：保留首版，另冻结使用 instr 的修订版，再用原索引重跑；没有换题，也没有修改算法去适配评分。

这仍有明确偏差：词语由人工选取，混排词先从同一语料发现；没有盲测、人工语义全库标注或跨语料泛化验证。

## Recall@10、Hit@10、MRR@10 各是什么？

- Recall@10：前十里的相关消息数除以全部相关消息数。若有2,485条相关，最多也只有10/2485，无法达到100%。总体57条正例Query的macro为9.772%→13.254%，按相关消息聚合的micro为459/147362→509/147362。
- Hit@10：前十是否至少出现一条相关消息，再按Query平均；总体54/57→56/57。
- MRR@10：首条相关结果排第r位，就计1/r；前十没有则为0。总体倒数排名和54→55，除以57。混排新增候选可能把相关结果向后挤，因此不能只看总命中数。

macro使每个Query同等权重，micro使每个相关消息对同等权重；常见词分母很大，两者回答不同的问题。空Reference单列无结果判定，不能补成满分Recall。

## 为什么命中增加不一定代表质量提高？

“agent开发”归一化后也可能命中“agent 开发”，其原始完整字面串不存在。语义上可能相关，但对字面Oracle是额外命中。全深度mixed额外命中339个，整体实际返回项字面Precision@10从459/461降至509/519；3个混排Query前十相关数下降。

20个高频双字Query，两侧前十均有200条相关；B虽然几乎补齐整个相关集合，Recall@10没有提升。这证明覆盖改善与排序改善需要分别测量。Agent还可能误述已找到的证据：本次一次真实答案把“人工智能”说成“三个字”，说明来源存在不等于答案事实正确。

## 当前有哪些局限？

单字“荐”仍为0/2504；四个单字Query的全深度覆盖仅20/44703。ASCII词内子串、混排ASCII前缀/后缀还会漏召回，例如“字节hrbp”“mdagent开发”。混排空格和标点被tokenizer视作边界，可能降低严格字面Precision。

可恢复快照之外还有217个未展开forward节点，所以“Reference穷举”只针对已保存正文。真实Agent的空结果回答会被“必须完整且为空”的最终校验拒绝；这不是Provider报错。7个完整配对里两侧各5/7完成，只有一个混排Case的必要字面证据改善，不支持稳定端到端质量提升。

性能方面，同一投影输入的FTS构建1.839s→4.842s、文件124.63→170.97MiB；320次/侧warm SQL样本中位0.223→3.158ms，P95为10.427→66.517ms。该延迟不含生产readiness、正文恢复、上下文或模型调用，不能宣传成线上工具SLA。

## 面试中不能写成的结论

“Agent准确率99.99%”“所有中文查询100%召回”“英文子串检索完全保留”“线上查询低于67ms”“8题证明模型质量稳定提升”均没有证据。允许引用的结论必须同时带上查询样本量、快照、字面GT口径、检索深度和代价。
