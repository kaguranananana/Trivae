# Evaluation 优化：证据账本与面试追问

本轮没有可信的答案质量提升，因此第五条突出评测工程、失败定位与候选否决。不要把下面的工程交付改写为“准确率提升”“稳定改善”或“fresh Holdout通过”。

## Agent 岗简历第五条

> **评测与质量治理：** 基于版本化 GT，在 81.2 万条消息冻结快照上完成 20 题 40 次真实 Agent A/B 及 4 次复测，沿召回、模型可见与最终引用分层定位失败；结合证据覆盖、事实引用复核和 Token 成本否决退化 Prompt 候选，保留逐题分母、Trace 与请求级预算账本。

可以追问的实测结果是“为何拒绝候选”，不是虚构的提升：开发目标Evidence11/19→8/19；调参外23/29→22/29且出现一次Query交付失败。补充复测显示内容有波动，不能把一次退化当成稳定因果。人工答案准确率 unavailable。

## 面试追问

### 为什么不能拿旧Benchmark直接计算提升？

旧基线为473,236条消息、旧代码和OpenCode Go Provider，本轮811,892条且使用官方Flash。工具、Prompt、预算和数据分布都演进了，差值混有多个因素。因此旧报告只用于找失败方向，当前A必须先在当前固定环境重新运行，再只改变一个treatment。

### 如何从Trace区分检索失败和生成失败？

先看完整Host结果是否含目标，再看实际model projection是否省略，最后看最终Evidence与正文。本轮开发19个目标A返回12、最终引用11，说明获取与选据分别有差距。工具题四目标在Host阶段就缺失；nanobot四目标都取得并引用，但仍有绑定/概括问题。不能用只记录前50个ID的旧摘要证明“从未召回”。

### 为什么没有最终采用回复链修复？

历史三个required_context确有reply关系，但当前其中一题已经恢复；另外两题的关键回复先在工具获取阶段缺失，给已返回消息增加reply字段不会让未取回内容出现。source cap与窗口也不是同一个因素。没有当前坏答案的单点因果证据，就不把它们混入主实验。

### 如何保证A/B公平？

固定同一SQLite副本、Case/GT、Provider、七工具、预算、模型设置和Standard路径。Candidate检查所有条件相等；只有显式基础Prompt差异可变，动态指令后缀仍逐字相同。冻结源码worktree执行，保留真实diff和commit。固定A→B顺序、缓存及单次样本仍有限制，不能宣称已消除所有混杂。

### 最终答案怎么评分？

执行交付、必要事实、关键证据、引用支持和核心需求共同决定，未审核为pending。机器只确认可解析来源、目标覆盖与执行事实；Assistant按实际附带来源做provisional复核。人工尚未完成，所以人工通过率 unavailable，不能把未审计答案全记pass。

### 引用存在为何还不够？

它只证明来源真实、属于当前Run和Scope。某个来源可能是另一话题的体验句，也可能只是项目发布，无法支持“实际使用效果”结论。本轮777次引用全能恢复，依然出现话题误归、日期合并和无据概括。正确事实在其他段落出现，也不自动修复这一结论的错误绑定。

### 如何避免为了Benchmark过拟合？

不把题目关键词、仓库名或消息ID写进产品规则；只试一项通用充分性澄清，不增预算；预登记12条不参与调参的问题，Candidate冻结后不继续改；公开失败与退化，拒绝没有收益的候选。历史Case仍已暴露，调参外验证不能称blind/fresh。

### 优化效果和代价是什么？

未获得可信提升。开发Evidence11/19→8/19，Token+11.74%、平均Query延迟+28.33%；调参外Evidence23/29→22/29，交付12/12→11/12，Token+22.65%。候选因此回退。额外复测说明部分内容会随机翻转，既不能挑后一次成功，也不能把第一次退化直接说成稳定因果。

### 为什么空日题HTTP200、Runtime完成却算失败？

B先读取其他日期SQL分组行，再取得目标日complete/0，最后用no_result形态承载其他结构化事实，Finalizer拒绝。HTTP200只表示传输成功，Runtime completed只表示模型循环结束，最终没有正式Artifact才是用户看到的交付事实。不能为提高分数放宽校验。

### 没有提升，为什么还值得写？

能将“跑完了”“引用真实”“找到相关内容”和“回答满足需求”分开，并用原始运行、Trace和成本证明一个看似合理的修改不值得发布。可写评测工程、根因定位、实验控制与质量门禁，不能写没有取得的准确率收益。
