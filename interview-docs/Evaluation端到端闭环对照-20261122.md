# Trivae `eval@v2` 端到端闭环对照实验报告 · 2026-11-22

> 本报告记录 2026-11-22 在冻结快照 `frozen-20261028-validated`（864,615 条消息、Canonical/词法/语义 revision 98835）上完成的 24 题端到端 A/B 对照实验。所有模型辅助评审（GPT-6.1 Sol / Medium，`eval-rubric-v2.1`）均为 `provisional`，尚未经独立人工全量复审；本报告不将模型评分均分宣称为人工金标准准确率。

## 1. 实验目标与背景

此前 [research/agent-quality-20261029/REPORT.md](../research/agent-quality-20261029/REPORT.md) 已完成两处语义检索中间层截断修复（合入 `main` 提交 `ce553277`）：
- **R2（Capability 容量层）**：[retrieval.py](../src/trivae/retrieval/semantic/retrieval.py) 在 100 条扩展上限内优先保留字面证据与高检索排名命中，而非按时间顺序淘汰（51 个固定 ANN 池离线重放中，Top-1 高分块整块丢失 `19/51 → 0/51`，已知目标按调用出现 `8 → 18`）。
- **R6（Host 预算裁剪层）**：[evidence.py](../src/trivae/query/evidence.py) 在 32K 工具结果预算裁剪 hit 时继续沿用上游 `primary_message_ids` 优先序（同一新 Capability 输出上模型可见目标 `10 → 14`）。

但此前端到端真实 Agent 对照仅跑了 4 道题（8 槽，样本过小），且 DeepSeek 在 `json_object` 模式下偶发于 JSON 字符串内输出未转义英文双引号导致 `AnswerDeltaParseError` 丢单（且实测 DeepSeek 当前端点对 `response_format={"type":"json_schema"}` 返回 HTTP 400 `This response_format type is unavailable now`）。

本轮完成三项收口：
1. **构建 24 题冻结评测集 `eval@v2`**（`evaluation/suites/eval-v2.json`，提交 `1722b13c`）：保留原 `eval@v1` 全部 16 题，并从自然用户候选池按参考消息去重与证据质量筛选新增 8 题；清理 2026-10-28 废弃草稿与重命名前重复题目。
2. **落地可观测的 JSON 引号容错**（提交 `4cb252d0`）：新增 [json_repair.py](../src/trivae/query/json_repair.py)，并在 [streaming.py](../src/trivae/query/streaming.py)、[evidence.py](../src/trivae/query/evidence.py)、[orchestrator.py](../src/trivae/query/orchestrator.py) 接入受限修复——仅转义 JSON 字符串值内部未转义的 ASCII `"`，修复后仍强制通过 100% 严格 `finalize_answer`（Schema/Scope/Provenance/Citation 零放宽），并在 Trace 与 `FinalizationDiagnostics` 显式记录 `repaired_unescaped_json_quotes` 与 `normalization_count`；全量后端回归 `1422 passed / 1 skipped`、`ruff`、`mypy`（149 文件）全通过。
3. **执行 24×2 同条件端到端对照与双维盲评**（脚本 [run_eval_v2_e2e_ab.py](../scripts/run_eval_v2_e2e_ab.py)，提交 `106ed339`）。

## 4. 典型可追溯案例（面试最硬核的因果证据）

1. **正向因果闭环最清晰：`cap1-24-recent-models`（任务 `2→4`，可信度 `2→3`，moderate 缺陷 `4→2`）**
   - **机制印证**：提问为“最近有什么模型适合写代码？群友试下来感觉如何？”（查询时点 10 月底）。Baseline 因按时间升序截断 100 条语义扩展，**早期 4–8 月消息先占满容量、直接把 10 月高相关块挤出窗口**，导致 Judge 明确诊断“主要介绍 4–8 月记录，遗漏 10 月项目体验，未解决‘最近’需求”；Candidate 保留高排名块后完整覆盖 10 月编码模型实践，任务满足度从 2 跃升至 4。
2. **首份零缺陷 4/4 满分答案：`cap1-17-context-cost`（任务 `3→4`，可信度 `3→4`，诊断 `2→0`）**
   - Candidate 覆盖全部核心优化路径（工具按需搜索/加载、短 Skill + 脚本、结果裁剪与日志量化），并准确区分群友“估计”、工具作者宣传与机器人转述，无任何过度外推，获双维 4/4 零缺陷评分。
3. **JSON 引号容错线上救单：`cap1-07-mcp-skills`（Candidate `4/3`，`valid`）**
   - Candidate 生成阶段实测出现 **4 处 JSON 字符串内未转义 ASCII 双引号**；新容错机制在流式回合末与 Finalizer 边界拦截修复，且修复后仍通过 100% 严格 Citation/Scope 校验，最终拿下 `4/3` 评分。若无该机制，该题会在流式阶段直接以 `AnswerDeltaParseError` 失败。
4. **诚实保留的负例与剩余瓶颈：`cap1-08-kimi-deepseek`（`3/3 → 3/2`）与 `cap1-14-agent-interview`（Candidate 预算失败）**
   - `cap1-08` 两侧均命中同一参考消息，但 Candidate 在回答综合时将单人未标明任务类型的体验外推为“写代码比较”与“群内主流口碑”，印证了**检索召回好转不能自动消除 LLM 的归纳越界**；
   - `cap1-14` 在 32K 共享池下触发同轮预算准入上限失败（Baseline 则在 `cap1-03`/`09` 触发两次同类失败），说明 32K 预算终止边界（在模型选出不可准入批次前优雅切入无工具综合）仍是下一步工程优化点。

## 5. 面试 90 秒口播与简历写法建议

### 面试官追问“检索召回修好后，端到端回答质量到底涨了多少？”怎么答

> “我专门补齐了这个闭环，没有只停留在离线召回率。我先在同一个 86.5 万条冻结快照上把原 16 题去重扩充成 24 题 `eval@v2`，同时针对 DeepSeek 不支持 `json_schema` 且偶发未转义引号的问题，在流式解析和 Finalizer 之间补了一层受限引号容错（严格保持 Citation/Scope 校验零放宽并在 Trace 留痕）。
>
> 然后固定同一模型、Prompt、7 工具和 `128K/32K` 预算，在两个独立 APFS 工作库里跑完 24 题修复前后对照，并用同一个盲评双维 Judge v2.1 逐题回读冻结原文评分。
>
> 结果很实在：**交付率从 22/24（91.7%）提到 23/24（95.8%）**，新加的 JSON 容错在 `cap1-07` 上直接救下一单 4 处未转义引号的 `4/3` 有效答案；**全量任务满足度达标率（≥3）从 79.2% 提到 87.5%（+8.3pp）**，双轴同时达标从 45.8% 到 50.0%，且**严格配对的 21 题里中等严重度缺陷从 49 项降到 39 项（-20.4%）**，其中时效/范围错误降 29.4%、关键信息遗漏降 33.3%，同时输入 Token 反而降了 10.2%。像近期模型选型题 `cap1-24`，修前因为按时间截断把 10 月高分块全挤掉了只拿到 2/2，修后直接涨到 4/3。
>
> 但我也没夸大结论：端到端均分提升相对温和（双轴各约 +0.05/+0.10），数据非常清楚地指出**原因在于检索修好后主瓶颈已经转移到了生成层的 `unsupported_assertion`（20→20 没降）**——模型拿到足够证据后仍习惯把个人体验外推成群体共识。这直接指明了下一阶段应该把投入从继续卷召回，转向 Claim 级的归属约束与后置校验。”

### 可直接替换/补充的简历第 5 条 Bullet（事实边界严谨）

> - **评测闭环与检索/解析治理：** 在 86.5 万条消息冻结快照上构建 24 题版本化评测集 `eval@v2` 与隔离 APFS 工作库跑测流程，落地双维盲评 Judge（任务满足度/回答可信度 + 结构化缺陷诊断）；针对语义检索容量/预算两层按时间截断缺陷及 DeepSeek `json_object` 偶发未转义引号崩溃，实现排名优先保留与可观测受限 JSON 引号修复（保持 Citation/Scope 严格校验）。离线固定 51 池 Top-1 高分块丢失 `19/51→0/51`、目标召回 `+125%`；24×2 端到端同条件对照交付率 `91.7%→95.8%`，任务满足度达标率 `79.2%→87.5%`（+8.3pp），配对中等缺陷数 `49→39`（-20.4%，时效/范围错位 -29.4%、关键遗漏 -33.3%），输入 Token `-10.2%`，并基于诊断数据定位下一主瓶颈为生成层过度外推（`unsupported_assertion` 持平 20→20）。
